CODE2RULE · 쉬운 설명판

코드 속에 갇힌 업무 지식을 꺼내,
검색하고 질문할 수 있게 만든다

본 문서는 사업 계획(WBS)의 내용을 전문 용어 없이 풀어 쓴 설명판이다. 용어가 불가피한 곳은 옆에 뜻을 병기했다.
기준 문서 — 일정·책임·검수 조건의 공식 기준은 「사업 실행 계획서(WBS) v1.0」 본문이며, 본 설명판과 본문이 다르게 읽히는 경우 본문이 우선한다.
01

사업 배경

현행 시스템의 업무 규칙 — 요금 계산, 청구 시점, 면제 조건 — 은 문서에 있지 않다. 전부 데이터베이스 안의 프로그램(오라클 패키지)에만 존재한다. 과거 문서는 유실되었고, 작성자들은 퇴사했다.

그 결과 지금은 코드 두 줄을 수정하려 해도, 해당 코드를 아는 사람을 찾아 확인하는 데 수 주가 걸린다. 아는 사람이 없으면 더 걸린다.

사업 요지 — 프로그램 코드를 AI가 읽어 사람이 읽을 수 있는 업무 설명서를 자동 생성하고, 설명서 서고에 채팅으로 질문하면 근거와 함께 답이 나오게 한다. "이 계산이 어디서 되는가"의 확인이 수 주에서 수 분으로 단축된다.

이 방식의 동작 여부는 기준 시스템(시연 환경)으로 직접 확인할 수 있으며, 착수 초기에 시연을 실시한다. 본 사업은 검증된 방식을 실제 대상 프로그램 148개에 적용하는 것이다.

02

구성 요소

이름쉽게 말하면
업무 설명서
(역문서)		 코드를 읽고 만드는 사람용 설명서. "이 프로그램이 무슨 일을 하고, 어떤 규칙으로 계산하는가"를 기술한다. 공통 문서 표준(OKF)을 따르므로 특정 도구에 종속되지 않고 읽고 검색할 수 있다.
지식베이스
(KB · LightRAG)		 설명서를 모아두는 검색 서고. 단어가 정확히 일치하지 않아도 의미로 찾는다.
웹 채팅 창구
(LibreChat)		 브라우저에서 쓰는 질문 창구. 현업 누구나 "OO는 어떻게 계산되는가"를 물으면 서고를 찾아 답한다.
전문가용 도우미
(OpenCode)		 개발자 PC에서 쓰는 AI 도우미. 서고와 소스 코드 파일을 함께 열어 오류 원인 추적(디버깅)과 수정 검토를 지원한다.
DB 확인 도구
(SQLcl)		 AI가 "코드가 이렇다"고 답할 때, 실제 데이터도 그런지 데이터베이스에서 직접 확인하는 통로. AI 발언을 신뢰로 받지 않고, 데이터로 검증하고 쓴다.
AI 엔진
(AWS Bedrock)		 설명서 생성과 질의 응답을 수행하는 AI 두뇌. 고객사 AWS 클라우드 내부에서만 동작하며, 소스코드는 외부로 나가지 않는다.

위 구성은 개념도가 아니라 동작하는 실물이며, 착수 초기 시연에서 확인한다.

03

작업 방식 — 세 동작의 반복

개발보다 공정에 가깝다. 프로그램 하나마다 아래 세 동작을 반복한다.

동작 1
넣기 (인제스트)
코드를 가져와 AI가 업무 설명서를 생성하고 서고에 적재한다. 어느 프로그램이 어디까지 진행됐는지는 관리 대장(진행 현황표) 한 장으로 추적한다.
동작 2
묻기 (쿼리)
현업이 실제로 궁금한 질문 20개(골든 질의)를 사전에 정해두고, 서고가 근거와 함께 제대로 답하는지 확인한다. 이 20개가 품질 시험 문제지다.
동작 3
채점 (평가)
생성된 설명서를 다른 AI가 원본 코드와 대조해 채점하고, 코드 호출 관계와도 기계적으로 대조한다. 저점 문서는 사람이 표본 검사한 뒤 재생성한다.
본 사업에서 새로 발명하는 것은 없다. 동작이 확인된 방법(설명서 작성 지침 · 채점 방법 · 진행 관리 방식)을 표준으로 확정하고, 고객사 환경에 조립해 148개에 반복 적용하는 것이 사업의 본체다. 관리 화면(백오피스) 등 추가 개발은 2단계에서 — 실제로 반복된 작업에 한해 — 수행한다.
04

산출물 — 사업으로 남는 것

산출물설명
업무 설명서 148건대상 프로그램 전체의 사람용 설명서 — 표준 양식(OKF), 검색 서고에 적재된 상태로 인도
검색 서고(지식베이스)고객사 환경 안에서 가동되는 검색·질의 시스템
질문 창구웹 채팅(LibreChat) — 승인 시 개발자용 도우미(OpenCode)까지 2종
운영 문서 세트관리 대장 · 소스 추출 절차서 · 설명서 작성 지침 · 품질 채점 기준서 담당자가 바뀌어도 같은 품질로 반복할 수 있게 하는 인수인계 문서.
실측 리포트리허설·표본 처리의 측정 기록 — 품질 목표 수치의 근거
(2단계) 자동화코드 변경 시 자동 재문서화 + 진행 현황 관리 화면(백오피스)

시스템만 남는 것이 아니라, 시스템을 계속 운영할 수 있게 하는 절차와 기준이 문서로 남는다.

05

일정 — 세 구간, 날짜가 아니라 조건

구간기간내용
준비착수 ~ 약 5주
(환경 불요)		 AWS 환경 없이 가능한 작업을 먼저 끝낸다. 수행사는 진행 대장·추출 절차·작성 지침·채점 기준을 확정하고 전 과정을 사전 리허설한다. 고객사 결정 사항은 항목별 1장 체크시트로 준비해, 미팅 자리에서 확인만으로 종결되게 한다.
구축AWS 개통 후
10주		 먼저 표본 처리로 "실제 환경에서도 리허설과 같은 품질이 나오는가"를 확인하고 목표 수치를 확정한다. 이후 148개 전체를 순서대로 처리해 서고를 채우고, 질문 창구를 연다.
운영서고 오픈 후 코드 변경 시 해당 설명서만 자동 재생성되게 연결하고, 진행 현황 관리 화면을 구축하며, 사용자를 확대한다. 상세 범위는 오픈 후 별도 협의한다.
일정은 날짜가 아니라 조건으로 정의된다. 구축 구간은 "9월 1일 시작"이 아니라 "AWS 환경 개통일부터 10주"다. 환경 개통이 늦어지면 일정이 그만큼 이동할 뿐 계획 실패가 아니며, 무엇이 열려야 다음이 시작되는지가 문서에 모두 드러나 있어 대기의 사유를 상호 확인할 수 있다.

고객사 결정 사항 — 7건

기술 작업은 수행사가 담당한다. 고객사 몫은 아래 결정이며, 모든 항목은 "불가" 결정 시의 대안이 준비되어 있다. 단, 결정 지연은 그대로 일정 지연이 된다.

#결정 사항
1AWS 관리 담당자 지정 — 계정·사용자·비용 관리 주체. 지정되어야 환경 개통이 시작된다. 전담 조직은 불필요하다. "누구에게 확인하면 되는가"가 정해지는 것이 핵심.
2웹 채팅 창구(LibreChat) 사용 승인 — 현업용 질문 창구.
3개발자 PC용 AI 도우미(OpenCode) 사용 승인 — 불가 시 웹 창구 단독으로 진행(기능 일부 축소).
4운영 데이터베이스의 읽기 전용 조회 가능 여부 — 가능하면 "코드와 실제 데이터의 일치"까지 검증할 수 있어 품질이 가장 높다. 불가 시 사본(스냅샷) 방식으로 진행한다.
5소스 코드 유통 경로 확인 — 형상관리(Bitbucket) 보유 여부, DBA 배포 조직 경유 여부에 따라 반입 방법이 달라진다.
6업무 전문가(SME) 질문 담당자 지정 — 코드만으로 알 수 없는 사항("이 예외는 왜 있는가")을 정기적으로 확인한다. 주 1회, 10건 이내로 부담을 제한한다.
7품질 시험 문제 20개 선정 — 평소 궁금하던 질문에 체크하면 그것이 품질 검사 기준이 된다. 후보 문항은 수행사가 사전에 제시한다. 백지 작성은 없다.
08

기술 선택 — "Lambda·Step Functions" 안에 대하여

초기 논의에서 AWS Lambda(서버 없이 코드를 실행하는 서비스)와 Step Functions(작업을 자동으로 연결하는 서비스) 기반의 구축안이 있었다. 유효한 도구이며, 폐기하는 것이 아니다. 적용 시점이 다를 뿐이다.

시점판단
지금 (1단계) 아직 절차 자체가 실측으로 확정되기 전이다. 자동화 도구를 먼저 고르면 절차를 도구에 맞추게 되어 순서가 뒤집힌다. 또한 AI의 설명서 생성은 장시간 작업이라 Lambda의 15분 실행 제한과 맞지 않고, 현 단계의 진행 관리는 관리 대장(현황표 한 장)으로 충분해 도구를 늘릴 이유가 없다.
2단계 (운영기) 구축 구간을 지나면 "어떤 작업이 실제로 반복되는가"가 기록으로 확정된다. 그 반복 작업을 자동화하는 시점(관리 화면·배치 구축)에 Step Functions를 실행 기반 후보로 포함해 검토한다. 자동화 대상이 확정된 뒤의 도구 선택은 안전하다.
요약 — 순서의 문제다. 절차를 먼저 확정하고(1단계), 자동화 도구는 그 다음(2단계). 이 순서면 어떤 도구가 선택되어도 절차는 그대로 유효하다.
09

예상 질문

소스코드가 회사 밖으로 나가는 것 아닌가.
나가지 않는다. AI 처리는 전부 고객사 AWS 클라우드 내부에서 이루어지며, "입력 내용이 AI 학습에 사용되지 않는다"는 정책을 문서로 확인하는 절차가 계획에 포함되어 있다. 코드를 옮기는 경로 자체도 보안 승인을 받은 공식 절차로만 만든다.
AI가 틀린 답을 하면 어떻게 되는가.
세 겹의 장치를 둔다. ① 모든 답변에 근거(어느 문서·어느 코드)가 붙는다 ② 확인되지 않는 것은 추정하지 않고 "확인 필요"로 답하도록 규칙화되어 있다 ③ 설명서 자체가 이중 채점(AI 채점 + 기계 대조)과 사람 표본 검사를 거친다.
고객사의 부담이 커지는 것 아닌가.
