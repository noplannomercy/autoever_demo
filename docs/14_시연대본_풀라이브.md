## 1. 라이브 질의 원문 (복사용 — 시연 중 이 문구 그대로, 즉흥 변형 금지)

**장면 1 — 탐지** (7페이지 끝에서 전환)
```
VIP 고객인데 중도해지 위약금이 부과된 계약이 있는지 확인해줘
```
→ 기대: 4건 표(계약 63·133·203·273) + 344만 원 + 회수규정_05 인용 + "면제 로직 검토·수정 필요" 자발 제안

**장면 2 — 사람 검증 ① (해석 제거)**
```
방금 그 4건, 이번엔 네 해석 없이 내가 직접 검증할게.
계약 ID를 하드코딩하지 말고, 규정 위반 조건만으로 찾는 검증용 SQL 한 개를 먼저 보여주고
그 SQL을 그대로 실행해서 원본 결과만 표로 보여줘. 요약이나 해석은 붙이지 마.
```
→ 기대: 조건식 SQL(VIP×중도해지×위약금×금액>0) 공개 → 원본 4행 (grade 전부 VIP, 상태 "완납")

**장면 3 — 원인 추적 (3단계, 같은 대화에서 순서대로)**
```
아까 그 4건의 위약금 금액이 정확히 원금의 2%던데,
이 계산을 시스템 어디서 하는지부터 찾아줘.
DB에 저장된 함수와 프로시저 목록을 스키마 포함해서 전부 조회해서,
위약금 계산 후보를 짚어줘.
```
→ 기대: pkg_collection 5함수 발견 + f_calc_penalty 지목 + 4건 2% 검증표(✅TRUE)
```
f_calc_penalty 함수의 소스 코드를 DB에서 그대로 꺼내서 보여줘.
가공하지 말고 원문 그대로.
```
→ 기대: 소스 원문 (2021-06 수기 정정 주석 포함)
```
이 소스에서 VIP에게 위약금이 부과된 원인이 되는 라인을 그대로 인용하고,
주석에 남아 있는 운영 방식의 단서도 짚어서, 왜 4건이 새어나갔는지 설명해줘.
```
→ 기대: 등급 미조회 지적 + 2021-06 주석 인용 + "수작업 의존, 수기 누락" 결론

**장면 4 — 수정안 (배포 금지)**
```
그 함수를 최소한의 수정으로 고치는 diff를 만들어서 보여줘.
고치는 줄에는 근거가 되는 규정 문서명을 주석으로 남겨.
배포는 절대 하지 말고, diff만 제시하고 멈춰.
```
→ 기대: 2줄 diff(JOIN+IF) + 회수규정_05 주석 + 승인 대기

**장면 5 — 사람 검증 ② (승인 — 범위 제한 필수)**
```
승인. 그 diff대로 함수만 교체해서 배포해줘.
데이터는 절대 건드리지 말고, 배포가 잘 됐는지는 조회로만 검증해서 보고해줘.
```
→ 기대: pg_execute 함수 교체만 + 검증 보고(VIP 42건 0원 / 일반 386건 그대로) + "billing 미수정, 환불 별도" 플래그

**장면 6 — 사람 검증 ③ (사람이 지정한 SQL)**
```
마지막 검증은 내가 한다. 아무 해석 없이 아래 SQL만 그대로 실행해서 결과만 보여줘.
SELECT pkg_collection.f_calc_penalty(63) AS vip_63, pkg_collection.f_calc_penalty(7) AS normal_7;
```
→ 기대: vip_63 = **0** / normal_7 = **340000**

## 3. 연출 원칙

1. **대기를 사과하지 않는다** — 툴 로그 중계가 곧 "에이전트가 일한다"의 실황. "이 기다림이 오늘의 숨은 주인공입니다."
2. **라이브 응답에서는 표의 숫자만 읽는다** — 서술부 집계는 어긋날 수 있음 (07-21 실측: "총 44건" 오차, DB는 42). 표의 건수·금액·계약ID·출처는 SQL 결과라 항상 정확.
3. **결과 숫자를 예고하지 않는다** — "4건이 나올 겁니다" 금지. 숫자는 화면이 먼저 말하게.
4. **검증된 질의만 사용** — 즉흥 변형·청중 즉석 질의는 받지 않는다. 요청 오면 "별도로 확인해 드리겠습니다." (근거: 에이전트가 대상을 못 찾으면 그럴듯한 코드를 지어낸 실측 사례 있음 — 07-21, 스키마 명시 전 STEP 질의에서 가짜 Python "표준 구현" 생성)
