# 시나리오 수용 검증 기준 (초안 v0.1)

> WBS 2.2(M3)·2.5(M5)의 판정 방법 · 2026-07-16
> 원칙: KB의 성패는 "문서가 만들어졌는가"가 아니라 **"실제 업무 시나리오를 만족시키는가"**로 판정한다.
> 같은 시나리오 세트를 2.2(표본) → 2.5(전량 적재 후) → 운영기 정기 평가(R-07②)에서 반복 사용한다.

## 1. 시나리오 유형과 만족 기준

모든 답변의 공통 기준(R-17): 근거(출처) 블록 포함 · 확인 불가 항목은 추정 없이 "확인 필요" 표기.

| 유형 | 대표 시나리오 | 만족 기준 |
|------|---------------|-----------|
| S1 소스 디버깅 | "이 오류/이상 금액이 왜 나왔나" — 원인 함수·조건 추적 | 해당 로직의 위치(패키지·함수)와 원인 조건을 근거와 함께 지목 |
| S2 리팩토링·변경 영향 | "이 함수/컬럼을 바꾸면 뭐가 영향받나" — 수정 전 영향 범위 | 영향 객체 목록이 의존성 스냅샷과 모순 없음 (누락 시 사유 확인 가능) |
| S3 도메인 정보 질의 | "이 업무 규칙·코드값·계산식의 의미가 뭔가" | 코드 사실은 역문서 근거로, 업무 해석은 지식층 근거로 답하고 둘을 혼동하지 않음 |
| S4 코드·데이터 대조 | "코드 규칙과 실제 데이터가 맞나" | **1.5 접근 수준 판정에 따라 활성/이연** |

- 시나리오 문항의 원천: 골든 질의 세트(1.8 선별지 유형 ①~④) + 드라이런 도출 세트. S1·S2는 실제 표본 패키지에 대해 과제형으로 추가 구성.
- 측정: 유형별 문항 수와 만족률을 기록. 목표율은 `[TBD — 2.2 실측 후 C2로 확정]`.

## 2. 불만족 시 라우팅 — "무엇이 돌아야 하는가"

불만족은 실패가 아니라 **원인 분류 후 정해진 워크플로우 가동** 대상이다. 판정 불가·원인 중복 시 아래 순서로 점검한다(검색→문서→지식→모델).

| # | 증상 | 원인 | 가동할 워크플로우 | 재측정 |
|---|------|------|-------------------|--------|
| R1 | 관련 문서가 검색에 안 걸림 | 검색·적재 문제 | 청킹·적재 방식 조정 (A5 대응) → 재적재 | 동일 문항 |
| R2 | 문서는 찾았으나 내용 부실·오류 | 역문서 품질 | 지침 보강(1.12 개정) → 해당 문서군 재생성 (R-07③) → 재검증(1.13) | 동일 문항 + 저지 재채점 |
| R3 | 코드에 답이 없는 질문 (업무 배경·사유) | 지식 공백 | `[SME 확인 필요]` 태깅 집계 → SME 질문 발송 (R-11) → 지식층 축적 | 답변 축적 후 |
| R4 | 생성 자체의 품질 한계 (지침으로 개선 안 됨) | 모델 한계 | A1 대응: 모델 변경 또는 프롬프트 재설계 → 표본 재실측 | 표본 전체 |
| R5 | 데이터 사실 확인 불가 | 접근 수준 | 1.5 판정 재확인 — 범위 이연 항목이면 "확인 필요"가 정답 (불만족 아님) | — |

- 라우팅 결과(원인 분류·조치·재측정 결과)는 관리 대장·실측 리포트에 기록한다.
- R2가 반복되는 문서군은 "재생성 횟수 n" 필드(검증 기준서 §5)가 지침 문제의 조기 신호.

## 3. 실행 시점별 역할

| 시점 | 표본 | 판정 |
|------|------|------|
| 2.2 (E+1~2주, M3) | Bedrock 전환 검증 표본 + 시나리오 세트 | A1 판정 · 처리량 실측 · **C1·C2 목표 수치 확정 → SRS v1.1** |
| 2.5 (E+8~10주, M5) | 전량 적재 후 동일 세트 | KB 오픈 판정 (§6 C1~C4) |
