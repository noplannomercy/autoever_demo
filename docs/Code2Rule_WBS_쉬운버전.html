3.4운영 역할·권한 확정ⓐ 역할표: AWS 관리 · 관리 화면 운영 · 품질 리포트 확인 · 전문가 창구 · 지식 관리 — 각각 누가 하는지 확정(관리 화면 인수의 조건) ⓑ 권한 구분(조회/운영/관리) → 로그인 체계로 구현 ⓒ 작업 기록(감사 로그)고객+공동O+8주~ (역할표는 3.2와 병행)역할표 · 권한 체계2단계 운영 협의의 실체
3.5사용자 확대 · 확대 여부 판단성과 지표(품질 실측 · 사용량 · 확인 대기 감소 · 처리 기간 단축)를 보고 판단: ① 다른 업무 영역의 프로그램으로 확대 ② 같은 방식을 백엔드·화면 코드에도 적용 — 절차와 도구는 그대로 재사용공동상시운영 지표 · 확대 제안서검수 지표와 연동

전제와 위험 — 깨지면 무엇이 움직이는가

이 계획이 딛고 선 전제들이다. 전제가 깨지는 것은 계획을 조정할 사유이지 실패가 아니며, 각 항목에 조기에 알아차릴 장치를 붙여 두었다.

#전제 / 위험깨졌을 때움직이는 것조기 확인 장치
R-0AWS 환경 개통(고객사 담당 1.3)이 8/20을 넘긴다구축 전체 대기구축·운영 일정이 같은 간격으로 이동 (준비 구간은 계속 진행)주간 확인 · M1 미팅에서 일정 약속
R-0aAWS 관리 담당자가 정해지지 않은 채 유지된다환경 개통 자체를 시작 못함 — R-0의 근본 원인개통 지연 + 운영 체계 협의 지연M1 미팅의 선결 안건
R-1DB를 볼 수 없거나, 시험용 DB의 데이터가 실제와 다르다사본 방식으로 전환 · 데이터 검증은 운영 구간으로 미룸품질 목표치가 접근 수준 기준으로 정해진다 — 품질의 상한은 접근 수준이 결정판정 G3 (~8/20)

R-3웹 채팅(LibreChat)마저 쓸 수 없다쓸 창구가 없어진다 — 서고를 만들어도 이용할 수 없음사업 효과 실현 불가 — 대체 방안 긴급 협의판정 G2 (시연~E)
