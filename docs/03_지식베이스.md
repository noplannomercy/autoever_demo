# 03. 지식베이스 (LightRAG)

> 회수 규정 13장 · 적재 파이프라인 · 검색 검증
> 작성일: 2026-06-19 · 상태: 초안 · 원본: `rules/회수규정_*.md`

## 0. 개요

LightRAG MCP가 조회하는 **사내 규정/institutional knowledge 역할**의 지식베이스다. 회수 업무 규정 **13장**(산문 마크다운)을 LightRAG에 적재해, 벡터+그래프(`mix`) 검색으로 "왜/규정상 어떻게"에 답하고 **출처 문서를 인용**한다.

- LightRAG: `http://127.0.0.1:9621` (auth disabled). 스토리지=Postgres, LLM=OpenRouter `gpt-4o-mini`, 임베딩=OpenAI `text-embedding-3-small`.
- 설계 원칙: **손으로 쓴 규정**(역문서화 아님). 제품의 지식층은 규정/약관/매뉴얼이며, 회수 담당자가 실제로 보는 문서를 모사한다.

## 2. 적재 파이프라인

```
rules/회수규정_*.md  ──(ingest_rules.mjs)──▶  POST /documents/text {text, file_source}
                                                   │ LightRAG 백그라운드 인덱싱
                                                   ▼  (entity/relation 추출 + 임베딩)
                                            검색 가능(mix = vector + graph)
```

- **`rules/ingest_rules.mjs`** — 폴더의 모든 `*.md`를 `/documents/text`로 POST. `file_source`=파일명.
- **중복 방지** — LightRAG는 `file_source`로 중복을 감지. 동일 파일 재적재 시 `409 already contains`로 스킵(신규만 `200`). 13장 재적재 시 기존 5장 409 / 신규 8장 200으로 확인됨.
- **`rules/clean_kb.mjs`** — KB 청소. 보존 접두 `회수규정_`만 남기고 나머지(옛 PoC junk) 삭제(`--yes`). dry-run 기본.
- 인덱싱 상태: `GET /documents` → statuses(`pending/processing/analyzing/processed`). 13장 → 약 1분 내 전량 `processed`.

## 3. 검색 동작 (lightrag-mcp)

도구 **`lightrag_query(query, mode)`** — LightRAG `/query` 래퍼.
- `mode` 기본 `mix`(벡터+그래프). `include_references:true` 강제.
- 응답에서 **본문에 실제 인용된 출처만 추려** "── 출처 문서 (LightRAG 검색) ──" 블록을 덧붙임 → 환각 방지·근거 강제.
- 응답 구조: `response`(답변, 인라인 `[N]` 인용) + `references[]`(`reference_id`, `file_path`).

## 4. 검색 검증 (2026-06-19)

규정 13장 규모에서 **갭 핵심 질의가 자기 규정을 1순위로** 집어내는지(retrieval 정확도) + 신규 주제도 잡히는지 확인. 전부 통과.

| 질의 | 1순위 출처 | 판정 |
|------|-----------|------|
| 입금 충당 우선순위 순서? | `회수규정_02` | ✅ 갭1 |
| NSF면 연체 어떻게 처리? | `회수규정_04` | ✅ 갭2 |
| VIP 중도해지 위약금? | `회수규정_05` | ✅ 갭3 |
| 독촉 연락 시간·횟수 제한? | `회수규정_11` | ✅ 신규 |
| 자산건전성 분류 단계? | `회수규정_10` | ✅ 신규 |

> 결론: 13장으로 규정집 현실감을 키웠는데도 갭 데모의 retrieval 정확도는 유지. KB를 더 키울 경우 동일 검증 재수행 권장.
