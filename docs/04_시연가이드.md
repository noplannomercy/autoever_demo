# 04. 시연 가이드 — 7막 아크

> "운영 담당자의 하루" — 탐색 → 조회 → 규정 → 갭발견 → 정정 → 검증 → **코드 수정·배포**
> 작성일: 2026-06-19 · 7막 추가: 2026-07-02 · 상태: 초안

## 0. 핵심 메시지

> **KB만 있으면 그냥 챗봇. 실데이터가 붙으면 진짜로 일을 한다. 코드까지 고치면 SDLC가 된다.**
> 한 에이전트가 **데이터(Postgres)**와 **규정(LightRAG)**을 스스로 골라 쓰고, 둘을 대조해 **갭을 찾고, 규정 근거로 정정하고, 스스로 검증**한다.
> 7막에서 한 발 더 — **갭을 만들어낸 원인 코드를 추적해 수정·배포·검증**한다. "2줄 고치려고 2주 확인"이 몇 분으로 줄어드는 장면.

각 막은 점점 세진다. 시간이 없으면 4막(갭) → 5·6막(정정·검증) → 7막(코드수정)만 해도 핵심은 전달된다. 시간이 있으면 1~3막으로 "도구가 뭘 할 수 있는지"를 먼저 깔아준다.

## 0-1. 준비 (시연 직전)

- **OpenCode는 반드시 `stage/` 폴더에서 실행** — autoever_demo 루트에서 실행하면 에이전트가
  `data/01_demo_data.sql`(갭 주입 스크립트)·시연가이드(대본)를 검색해 **"의도적으로 심은 갭"이라고
  실토한다**(2026-07-02 실측). stage에는 opencode.json + AGENTS.md + legacy_src만 둔다.
- MCP 게이트웨이 생존: `SETUP.md §2-1` (tools/list → 200).
- OpenCode 실행 후 "사용 가능한 MCP 툴 보여줘" → `pg_query`/`pg_execute`/`lightrag_query`.
- **정정(5막)·코드배포(7막)는 상태를 바꾸므로 항상 맨 끝**. 시연 후 `§리셋`으로 원복(데이터+코드).
- 패키지 배포 상태 확인: `SELECT pkg_collection.f_calc_penalty(63);` → **1460000**(버그 버전). 0이 나오면 수정판이 남아 있는 것 — §리셋의 코드 원복부터 실행.

## 1막 — 탐색 (스키마): "이 시스템에 뭐가 있나"

도구: `pg_query`(information_schema). 에이전트가 **구조를 스스로 파악**하는 모습 → "사전 지식 없이 레거시를 읽는다"는 인상.

질의 예:
```
회수 관련 테이블들 구조 보여줘. 어떤 테이블이 있고 뭘로 연결돼 있어?
deposit_detail 테이블 컬럼이랑 의미 설명해줘
```
기대: 8테이블·FK 관계 요약. **모든 테이블·컬럼에 한글 COMMENT(dict)가 박혀 있어**, 에이전트가 `col_description`/`\d+`로 컬럼 의미를 인라인으로 읽는다(예: `alloc_seq` = "충당 순서… 규정: 연체이자→이자→원금→수수료"). → 실 레거시 데이터 사전 모사. (사전 문서 `회수규정_13`은 보조)

## 2막 — 운영 조회 (데이터만): Postgres 단독

도구: `pg_query`만. LightRAG는 안 부른다(단일 도구 = 대조군). **다양하게 보여줄 메뉴:**

```
이번 달 미납 청구 몇 건이고 총액 얼마야?
연체 3단계(장기연체) 계약 목록 보여줘
상품유형별 계약 수랑 평균 금리 뽑아줘
계약 1번 상환 스케줄 보여줘
자동이체 실패(NSF) 건수 알려줘
VIP 고객 몇 명이고 등급 분포는?
중도해지된 계약 몇 건이야?
```
기대: 각 질의가 `pg_query`만 사용, 실수치 반환. (예: NSF 234건, 미납=연체 계약 청구분)

## 3막 — 규정 확인 (KB만): LightRAG 단독

도구: `lightrag_query`만. 규정 13장을 넓게 보여준다. **출처 인용**이 항상 따라온다.

> ※ KB에 역문서(코드 문서)가 함께 들어간 뒤로는, 질의에 **"규정상"**을 붙여야 규정 문서가 1순위로 인용된다(실측: "입금 충당 우선순위 순서가 뭐야?" → 역문서 인용 / "**회수규정상** 입금 충당 우선순위는?" → 회수규정_02 인용). 3막 질의는 아래처럼 "규정상"을 붙여 던질 것.

```
입금 충당 우선순위 순서가 뭐야?                         (회수규정_02)
연체 3단계 구분 기준이 뭐야?                            (회수규정_03)
자동이체 실패하면 어떻게 처리해야 해?                    (회수규정_04)
VIP 중도해지 위약금은 어떻게 돼?                         (회수규정_05)
연체이자는 어떻게 계산해?                               (회수규정_07)
중도상환수수료랑 중도해지위약금이 뭐가 달라?             (회수규정_08)
연체 채권 자산건전성 분류 단계가 뭐야?                   (회수규정_10)
독촉 연락할 때 시간·횟수 제한 있어?                      (회수규정_11)
연체정보 신용기관 등록은 언제 해?                        (회수규정_12)
status 코드값이랑 bill_type 종류 알려줘                  (회수규정_13)
```
기대: 각 답변에 해당 규정 문서 인용. **이 단계까지만 보면 "그냥 똑똑한 챗봇"** — 4막이 반전.

## 4막 — 갭 발견 (융합): 둘 다 써야만 나오는 답 ★

도구: `lightrag_query` + `pg_query` **둘 다**. 규정과 실데이터를 대조해 위반을 찾는다. **기대 건수는 데이터로 확정**(문서 02 §4)이라 흔들리지 않는다.

### 4-1. 충당 순서 위반 (6건)
```
이번 달 입금 중 충당 순서 규정을 위반한 건 있어?
```
→ 규정(연체이자→이자→원금→수수료) vs `deposit_detail` 대조 → **6건** (contract 1,2,3,4,6,8). "원금이 1순위로 먼저, 연체이자가 3순위 = 위반."

### 4-2. NSF 연체전환 누락 (5건)
```
NSF(자동이체 실패)인데 연체 전환 안 된 계약 찾아줘.
```
→ `deposit.nsf_yn='Y'` vs `delinquency` 부재 + 규정_04 → **5건** (contract 11,22,33,44,55).
> 에이전트가 **"계약 상태론 연체지만, 정식 연체전환 기록(delinquency)이 빠진 5건"**으로 미묘함까지 짚으면 베스트. "상태는 연체로 보여도 처리 기록이 없어 채권 보전에 공백" — 이 한 줄이 임팩트.

### 4-3. VIP 위약금 오부과 (4건, ₩3,440,000)
```
이번 분기 중도해지 중 위약금 정책 위반 있어?
```
→ `billing` 위약금+VIP vs 규정_05(VIP 면제) → **4건** (contract 63,133,203,273, 합 ₩3,440,000).

### (보너스) 규정×데이터 추가 융합
```
연체 3단계(60일 이상) 계약 목록 뽑고, 규정상 추심을 몇 단계로 처리해야 하는지 알려줘
장기연체(3단계) 계약은 자산건전성 분류 기준으로 어디에 넣어야 해?
```
→ `delinquency`(stage='3단계', 실데이터 존재) + 규정_11(추심 단계)/_10(자산건전성) 대조. (시간 남을 때, 융합이 킬러 3종 말고도 가능함을 과시)
> ※ 데이터상 연체일수 최댓값은 80일이라 "90일+ CB 등록 대상" 같은 질의는 0건 — 그건 KB 단독 질의(3막)로만 다룬다.

## 5막 — 조치 / 정정 (쓰기): detect → fix ★★

도구: `pg_execute`. **4막에서 찾은 갭을 규정 근거로 직접 고친다.** 이게 "챗봇"과 "업무 에이전트"를 가르는 결정타.

```
방금 VIP 위약금 오부과 4건, 회수규정_05(VIP 전액 면제)에 따라 위약금 0으로 정정해줘.
```

기대 동작 (AGENTS.md 쓰기 안전수칙):
1. **실행 전 계획 제시** — 어떤 행을 어떻게 바꿀지 + 실행할 UPDATE 문 먼저 보여줌.
2. **before 조회** — 대상 4건(contract 63,133,203,273) 현재 위약금 금액.
3. **pg_execute 실행** — `UPDATE billing SET amount=0 WHERE bill_type='중도해지위약금' ...(VIP 4건)`. → `rowCount=4`.
4. **after 조회 + 규정 근거** — 정정 후 위약금 0 확인, "회수규정_05 VIP 면제 근거."

> ⚠️ 안전장치: WHERE 없는 UPDATE 금지(AGENTS.md). 범위는 식별자(contract_id)로 한정. 읽기는 pg_query, 쓰기만 pg_execute.

## 6막 — 검증 (재조회): fix → verify ★

도구: `pg_query`. 정정이 실제로 먹었는지 **에이전트가 스스로 재확인**.

```
다시 확인해봐 — 이제 VIP 위약금 정책 위반 건 남아 있어?
```
기대: 4막 4-3과 **같은 조회 → 0건**. "정정 완료, 위반 해소." → **detect→fix→verify 루프 완성.**

## 7막 — 원인 추적과 코드 수정: root-cause → patch → deploy → verify ★★★

도구: `lightrag_query` + `pg_query` + 로컬 소스(`legacy_src/pkg_collection.sql`) + `pg_execute`(배포).

> **연결 멘트(6막에서 이어받기):** "방금 4건을 정정했습니다. 그런데 이 오부과, 왜 생겼을까요?
> 다음 분기에 또 생깁니다. 원인이 코드에 있으니까요."

### 질의 1 — 원인 추적
```
VIP 위약금 오부과, 데이터 정정은 했는데 재발 안 하게 근본 원인을 찾아줘.
위약금이 어느 코드에서 어떻게 계산되는지부터.
```
기대: `역문서_PKG_COLLECTION` 인용 → `pkg_collection.f_calc_penalty`(151~178행) 지목 →
**"등급을 조회하지 않는다 + 등급별 면제는 영업지원팀 수기 정정으로 운영 중(2021-06 주석)"** 발견 →
규정_05(VIP 전액 면제)와 대조 → "수기 정정 관행이 4건을 빠뜨린 것, 근본 원인은 코드의 면제 로직 부재."
**여기가 킬러 장면** — 사람이 매번 고치는 프로세스는 구멍이 난다는 걸 코드 주석이 증언한다.

### 질의 2 — 영향도
```
이 함수 고치면 뭐가 영향받아? 지금 VIP 중도해지 계약이 몇 건이고,
일반 고객 위약금은 그대로여야 해.
```
기대: `pg_query`로 VIP/일반 중도해지 건수·위약금 분포 제시. "수정 영향 = VIP만, 일반은 불변."

### 질의 3 — 수정·배포 (2줄 패치)
```
회수규정_05에 맞게 legacy_src/pkg_collection.sql의 f_calc_penalty에 VIP 면제를 반영해줘.
diff 먼저 보여주고, 내가 승인하면 배포해.
```
기대 diff (정답지):
```sql
 DECLARE
   v_principal bigint;
   v_status    text;
+  v_grade     text;
 BEGIN
-  SELECT lc.principal, lc.status
-    INTO v_principal, v_status
-    FROM loan_contract lc
+  SELECT lc.principal, lc.status, c.grade
+    INTO v_principal, v_status, v_grade
+    FROM loan_contract lc
+    JOIN customer c ON c.customer_id = lc.customer_id
    WHERE lc.contract_id = p_contract_id;
   ...
+  IF v_grade = 'VIP' THEN RETURN 0; END IF;  -- 회수규정_05: VIP 전액 면제
```
→ **사람이 diff 승인(체크포인트 — 통제는 사람에게 있음을 보여주는 장면)** → `pg_execute`로
`CREATE OR REPLACE FUNCTION` 배포. 파일(진실원천) 수정 → DB 반영 순서 강조.

### 질의 4 — 배포 검증
```
배포 잘 됐는지 검증해 — VIP 중도해지 계약(63번)이랑 일반 중도해지 계약 하나씩 위약금 계산해봐.
```
기대: `f_calc_penalty(63)=0`(VIP 면제 적용), 일반 계약은 원금×2% 그대로.
"원인 제거 완료 — 다음 분기부터 오부과 자체가 발생하지 않는다." + **역문서 갱신·재적재 제안**
(→ "문서는 깨진다"는 대전제의 해답: 문서를 코드에서 다시 뽑으니 낡지 않는다).

### 클로징 멘트

## 세일즈 포인트 (현대캐피털/오토에버)

1. **KB만 vs 데이터 결합** — 규정 Q&A는 흔하다. **실데이터와 대조해 갭을 찾는 순간** 가치가 폭발(4막).
2. **detect → fix → verify 루프** — 찾기만 하는 게 아니라 **규정 근거로 정정하고 스스로 검증**(5·6막). 운영 자동화로 직결.
3. **추적성·근거** — 데이터 출처(테이블·행ID)와 규정 출처(문서명) 제시. 감사·신뢰성.
4. **미묘함을 읽는다** — "상태는 연체인데 기록은 누락"(4-2) 같은 데이터 구조의 함정까지 판단.
5. **환각 방지** — 없으면 "없음", 인용은 실제 검색 문서만. 금융권 신뢰 요건.
6. **도메인 무관 제품성** — 회수는 무대. "트랜잭션 DB + 사내 규정"이면 어느 업무·산업에도 이식.

## 시간 배분

| 판 | 구성 | 시간 |
|----|------|------|
| 임팩트판 | 4막(갭3종) → 5·6막(정정·검증) → 7막(코드수정) | ~10분 |
| SDLC판 (역순) | 7막 먼저(완성품) → "이걸 구성하는 부품이…"로 1~4막 요약 | ~10분 |
| 풀판 | 1막 → 7막 전체 | ~20분 |

> **SDLC판**은 "우리가 생각한 건 SDLC"라는 피드백을 받은 청중용 — 제일 센 장면(코드 수정·배포)을
> 먼저 보여주고 부품(질의·규정·갭탐지)으로 내려온다. 비전공 청중은 부품→완성품 순서로는 다리를
> 못 놓지만, 완성품→부품 순서는 따라온다.
