> 작성: 2026-07-14 (합성 3유형 실측 검증 완료 시점)
> 검증 기록: `C:\workspace\openwiki\docs\TEST_RESULTS.md`, `TEST_RESULTS_1227.md`

## 1. 개요

레거시 소스(DB 함수/패키지)를 **전용 서비스 없이** 에이전트 + 지침 + OKF
포맷으로 역문서화하고, 로컬 지식과 서버 지식(LightRAG 규정 KB, 실데이터
DB)을 **합성**해서 온보딩·분석·수정을 빠르게 하는 체계.

핵심 구조 — 지식은 세 곳에 나눠 산다:

| 위치 | 지식 성격 | 답하는 질문 |
|------|----------|------------|
| 로컬 `okf/` 번들 | as-is (변화 잦음) | 코드가 실제로 어떻게 동작하나 |
| 서버 LightRAG | should-be (변화 느림) | 규정상 어떻게 동작해야 하나 |
| 서버 DB (pg_query) | evidence | 실제로 무슨 일이 벌어졌나 |
| 로컬 `smes/` `refs/` | 보강 (서버 공백 메움) | 규정에 없는 판정 기준·데이터 이상의 맥락 |

## 2. 표준 폴더 구성

**대원칙: 원료는 `raw/`, 지식은 `okf/` — 최상위는 이 이분법이다.**

```
<project>/                      ← 로컬 git 저장소 (관리 단위)
├── AGENTS.md                   # 프로젝트 프롬프트: 서버 툴 사용법 + 로컬 라우팅 블록(§8)
├── instructions/               # 역문서화 지침 (okf-postgres / okf-oracle / okf-docs)
├── raw/                        # 원료 전부 — 진실원천. 하위는 원본 형태 보존(자율)
│   ├── code/                   #   소스 (함수·패키지·스키마 DDL)
│   ├── docs/                   #   문서 원료 (규정·매뉴얼·회의록)
│   └── scripts/                #   export·시드·배포 스크립트
├── okf/                        # 지식 번들 (OKF v0.1) — 하위는 §2.1 표준 카테고리만
│   ├── index.md                #   번들 진입점 + 역할분담 명시
│   ├── functions/  tables/     #   코드 유래
│   └── rules/  terms/  …       #   문서 유래
├── smes/                       # 전문가 유권해석 (규정 공백 보강, 서버 미적재)
└── refs/                       # 인시던트 기록·참고자료 (데이터 맥락, 서버 미적재)
```

- 같은 도메인의 코드·문서 지식은 **한 번들**에 산다 — functions/ 문서가
  /rules/ 문서를 크로스링크하는 것이 이 구조의 핵심 가치.
- raw/ 하위 구조는 표준을 강제하지 않는다 — 레거시 export가 오는 모양
  그대로 보존한다 (기존 프로젝트의 legacy_src 등은 소급 개명하지 않음).

- 원본 지침: `C:\workspace\openwiki\instructions\okf-postgres.md` (PL/pgSQL),
  `okf-oracle.md` (PL/SQL — Robotics 프롬프트 픽스의 원천)
- 신규 프로젝트에는 지침을 복사해서 자기 완결로 유지한다.

### 2.1 번들 표준 구조 (조직 프로파일 — 임의 변경 금지)

OKF 스펙은 디렉토리 구조를 정의하지 않는다(§3, 생산자 자유). 그러나 폴더명은
에이전트 라우팅 키이자 크로스링크 경로이므로 **조직 표준으로 고정한다.**
1급 디렉토리는 아래 7종만 사용하고, 새 종류가 필요하면 이 매뉴얼을 먼저
개정한다.

| okf/ 하위 | 담는 개념 | frontmatter type 예 | 소스 유형 |
|-----------|----------|--------------------|----------|
| `functions/` | 코드 실행 단위 (패키지·함수군·프로시저) | `PL/pgSQL Function Group`, `Oracle Package` | 코드 |
| `tables/` | 데이터 구조 (테이블·뷰) | `PostgreSQL Table`, `Oracle View` | 코드/DDL |
| `rules/` | 규칙·정책 | `Business Rule` | 문서 |
| `processes/` | 업무 절차·플로우 | `Process` | 문서 |
| `terms/` | 용어·코드값 사전 | `Term` | 문서/코드 |
| `references/` | 시스템·조직·외부 연동 | `Reference` | 문서 |
| `playbooks/` | 장애 대응·운영 절차 | `Playbook` | 문서 |

- 각 디렉토리에 `index.md` 필수 (한 줄 형식: `- [제목](파일.md) — description 그대로`)
- 파일명: 객체는 소문자 객체명(`pkg_collection.md`), 문서 유래 개념은
  한글 슬러그 허용(`중도해지환불정산.md`) — 단 공백 금지(밑줄)
- `smes/`와 `refs/`는 **okf/ 밖** 최상위에 둔다 — 권위 의미가 다른
  보강층이므로 번들(as-is)과 섞지 않는다
- 크로스링크는 항상 번들 루트 절대경로(`/tables/xxx.md`) — 이 표준이
  깨지지 않는 한 링크는 영구 안정
- **혼동 주의**: 프로젝트 루트의 `rules/`(LightRAG 인제스트용 원료)와
  번들의 `okf/rules/`(Business Rule 개념 문서)는 별개다 — 전자는 원료,
  후자는 산출물. 문서 원료 폴더는 `docs_raw/`로 명명해 구분을 권장.
- 문서→위키 지침: `instructions/okf-docs.md` (개념 경계·모순 처리·공백
  지적 규칙 — 코드 지침과 별도)
- **번들 1개 = 도메인 1개.** 한 저장소에 여러 도메인이 있으면(파일럿·
  모노레포 등) 서브프로젝트로 분리해 각자 okf/를 갖게 한다 — 무관한
  도메인이 한 번들에서 크로스링크되면 안 된다. 예: openwiki 저장소의
  pilot-code/ · pilot-docs/ 분리.

## 3. 신규 프로젝트 셋업 체크리스트

1. [ ] 소스를 파일로 확보해 로컬 git에 몰기 (오라클이면 SQLcl
       `DBMS_METADATA.GET_DDL` export → `src/`)
2. [ ] `instructions/okf-<방언>.md` 복사 (방언 다르면 번안)
3. [ ] `okf/`, `smes/`, `refs/` 빈 폴더 생성
4. [ ] AGENTS.md 작성: 서버 툴 규칙 + **로컬 지식층 라우팅 블록**(§8 템플릿)
5. [ ] 전역 소스 권위 규칙 확인 (`~/.config/opencode/AGENTS.md` — §8)
6. [ ] 역문서화 실행(§4) → 검수 → 커밋

## 4. 역문서화 실행

에이전트(opencode/Claude Code)에 한 줄:

> "src/의 소스를 instructions/okf-<방언>.md 지침에 따라 okf/에 역문서화해줘"

지침이 강제하는 것: 스펙만 말고 **바디까지** 읽기, 개념당 문서 1편, 산문
서술체, 매직 넘버 의미 해석(+근거 없으면 "추정" 표시), 크로스링크,
"주의 지점" 섹션(삼켜지는 예외·트랜잭션 경계·하드코딩), index.md 갱신.

**갱신 규칙(현행화)**: 소스를 수정한 커밋은 같은 커밋 단위에서 해당 okf/
문서와 index.md를 갱신한다. AGENTS.md에 규칙으로 박아둔다.

**품질 채점 기준** (검증 완료된 5항목):
- [ ] 업무 규칙이 표 나열이 아닌 산문인가
- [ ] 매직 넘버·상태 코드 의미를 짚고 추정 표시했는가
- [ ] 의존성이 크로스링크로 표현됐는가
- [ ] 위험 지점(WHEN OTHERS 삼킴 등)을 지적했는가
- [ ] frontmatter가 OKF v0.1 준수인가 (type 필수, description 한 문장)

## 5. OKF 문서 규격 (요약)

```yaml
---
type: PL/pgSQL Function Group | PostgreSQL Table | SME Note | Reference  # 필수
title: 사람이 읽는 이름
description: 딱 한 문장 (index.md에 그대로 실림)
resource: postgres://<db>/<schema>/<객체>   # 출처 판별의 핵심 — 반드시 실제 대상 시스템
tags: [업무도메인, ...]
timestamp: ISO8601
augments: 회수규정_05_...                    # smes/refs 전용 — 보강하는 서버 문서 명시
---
```

본문 순서(함수군): 산문 개요 → # 공개 인터페이스(표) → # 업무 규칙(산문)
→ # 의존성(+규정 매핑 표) → # Examples → # 주의 지점 → # Citations

- 크로스링크는 번들 루트 절대경로(`/tables/xxx.md`), 존재하는 문서에만.
- **규정 매핑 표**가 합성의 라우터다: 함수별로 "규정 문서(lightrag_query
  대상) / 관련 테이블(pg_query 대상)"을 표로 명시.
- 개선 예정: 라인 번호 인용(`소스.sql:151-174`) 병기 — 코드 점프용.

## 6. 지식 배치 규칙 (뭘 어디에)

| 지식 | 위치 | 이유 |
|------|------|------|
| 규정·정책 (should-be) | LightRAG | 변화 느림, 팀 공유 |
| 코드 역문서 (as-is) | 로컬 okf/ 만 | 변화 잦음(git 커밋으로 현행화), 규정과 의도적 모순이라 같은 KB에 넣으면 병합 오염(실측) |
| 유권해석·실무 기준 | 로컬 smes/ | 규정 공백 보강 — RAG는 공백에서 환각하며 비재현적(실측) |
| 인시던트·참고자료 | 로컬 refs/ | 데이터 이상의 맥락은 서버가 모름 |
| 사고 조사 보고서 | 시연·테스트 전 서버 적재 금지 | 에이전트가 정답을 검색해버림 |

## 7. 서버 승격 (로컬 역문서 → LightRAG) — 원자적 교체 필수

as-is 문서를 서버에 올릴 때(팀 공유 목적 등)는 반드시:

1. 구판 삭제: `DELETE /documents/delete_document {"doc_ids":[...]}` (X-API-Key)
2. 신판 적재: `POST /documents/text {"text":..., "file_source":"파일명"}`
3. LLM 캐시 클리어 (또는 질의 문구 변경 안내)

**구판·신판 공존 금지** — 실측: 공존 시 신판을 인용하면서 구판 내용으로
답하는 병합 오염 발생. 적재 확인은 `GET /documents`에서 processed 상태 폴링.

## 8. 프롬프트 3층 구조 (검증 완료)

**1층 — 전역 소스 권위 규칙** (`~/.config/opencode/AGENTS.md`,
SOURCE-AUTHORITY 마커 블록): 서버가 기준, 로컬은 검증 대상. 로컬 소스를
결론 근거로 채택하기 전 ①출처 일치(resource URI/스키마명 대조) ②산식
재현(실데이터 재계산) — 불일치 시 기각. 근거 분리 인용.
→ 효과(실측): 그럴듯한 픽스처 코드를 스스로 기각하고 진짜 원인에 도달.

**2층 — 프로젝트 라우팅 블록** (프로젝트 AGENTS.md, 템플릿):

```markdown
<!-- LOCAL-KNOWLEDGE:START -->
## 로컬 지식층 라우팅
- 코드가 실제로 어떻게 동작하는가 (as-is) → `okf/` (진입점 okf/index.md)
- 규정에 없는 판정 기준·실무 해석 → `smes/` (규정 공백 주제는 서버 단독 답변을 신뢰하지 말고 반드시 대조)
- 데이터 이상 현상의 원인·맥락 → `refs/`
서버 규정과 로컬이 충돌하면 서버 기준으로 갭 보고, 서버 공백을 로컬이
보완하면 로컬 채택(출처 명시).
<!-- LOCAL-KNOWLEDGE:END -->
```
→ 효과(실측): 자연형 질문에서도 smes/를 자발 참조, RAG 공백 환각 상쇄.

**3층 — 문서 내 포인터**: okf/ 문서의 규정 매핑 표·검증 포인트가 에이전트를
나머지 자원으로 라우팅.

## 9. 합성 검증 시나리오 (새 프로젝트 적용 시 재사용)

지시형/자연형 2패스로 실행, 2×2 판정 (둘 다 성공=완성 / 지시형만=라우팅
보강 / 둘 다 실패=배관 수리):

| 유형 | 대표 질의 | 합격 기준 |
|------|----------|----------|
| 충돌형 | "이 함수 로직이 규정에 맞아?" | 양쪽 인용 + 갭 판정 |
| 보강형(공백) | 규정에 없는 판정 기준 질문 | 서버+smes 결합, 기각 안 함 |
| 보강형(맥락) | "이 데이터 이상 왜 생겼어?" | 검출(서버)+원인(refs) 결합 |
| 승격형 | 로컬 고유 사실을 서버 단독 질의 | 적재 후 정답 (적재 전 실패 확인) |

## 10. 함정 목록 (전부 실측)

1. **Windows 셸 한글 인코딩** — curl -d로 한글 body 전송 시 CP949 깨짐 →
   no-context 오진. API 호출은 반드시 UTF-8 보장 경로(파이썬 등).
2. **LightRAG LLM 캐시** — 같은 문구 재질의 시 문서 갱신 후에도 옛 답 반환.
   테스트·시연 시 문구 변형.
3. **픽스처 디코이** — 워크스페이스의 합성 샘플 코드를 실조사 원인으로
   오특정. 전역 권위 규칙(1층)으로 차단.
4. **RAG 공백 환각** — 규정에 없는 주제에 그럴듯한 답을 지어내며 매번 다름.
   smes/ 보강 + 라우팅 블록으로 상쇄.
5. **구판·신판 공존 오염** — §7 원자적 교체로 차단.
6. **시연 시 갭 주입 스크립트 노출** — 에이전트가 데모 시드(data/)의 의도적
   갭 로직을 찾아 폭로함. 시연 체크아웃에서 data/ 등 "무대 뒤" 파일 제거.
7. **테스트 오염** — 정답이 적힌 기록 파일(TEST_RESULTS 등)이 워크스페이스에
   있으면 에이전트가 읽음. 블라인드 테스트 시 제거.
