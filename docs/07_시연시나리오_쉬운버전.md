# 07. 시연 시나리오 — 쉬운 버전 (사람 검증 포함)

> 작성: 2026-07-02 · 컨셉: VSCode 한 화면에서 **에이전트(OpenCode)가 일하고, 담당자(SQLTools)가 검증한다**
> 전체 소요: 12~15분 · 구조: 무대 소개(장면 0) → 에이전트가 3번 일하고(찾기·원인·수정), 사람이 3번 검증한다(데이터·diff·결과)

## 화면 구성

```
┌─────────────────────────┬─────────────────────────┐
│  OpenCode (에이전트 채팅)   │  SQLTools (데이터 직접 조회) │
│  - 질문하고 답 받는 곳       │  - 에이전트 말을 검증하는 곳   │
└─────────────────────────┴─────────────────────────┘
```

- SQLTools 연결: `demo_legacy (오토에버 데모)` — 이미 설정됨

  (0이 나오면 수정판이 남은 것 — 하단 §원복의 코드 원복 먼저)

## ⚠️ 실행 위치 — 반드시 stage 폴더에서 (4번째 벽)

**OpenCode는 반드시 `stage/` 폴더에서 실행한다.** VSCode도 `stage/`를 워크스페이스로 여는 것을 권장.

```
autoever_demo/stage/     ← 시연 무대. opencode.json + AGENTS.md + legacy_src/ 만 있음
```

이유(2026-07-02 리허설 실측): autoever_demo 루트에서 실행하면 에이전트가 근본원인을 찾다가
`data/01_demo_data.sql`(합성데이터 생성 스크립트)까지 검색해서 **"이 4건은 데모용으로 의도적으로
주입된 갭"이라고 결론에 써버린다.** 시연가이드(대본)·플랜 문서도 같은 폴더에 있으므로 노출 위험 동일.
무대 폴더에는 운영 담당자가 실제로 가질 파일(소스·지침·연결설정)만 둔다.

## 장면 0 — 무대 소개: "지금 보실 시스템은 이렇습니다" (2~3분)

다짜고짜 문제로 들어가지 않는다. 청중이 처음 보는 시스템이므로 **무엇이 있는지**부터 깔아준다.

### 0-1. 진행자 소개 (그림 한 장, 30초)

> "가상의 여신/할부 회사입니다. 실제 회사처럼 세 층으로 되어 있습니다."

```
┌── 규정집 (LightRAG 지식베이스) ─────────────────────┐
│   회수규정 13장 + 코드 역문서 1건                      │
│   "어떻게 해야 하는가"                                │
├── 업무 데이터 (PostgreSQL demo_legacy) ─────────────┤
│   고객 2,000 · 계약 3,000 · 상환스케줄 12,600         │
│   청구 2,500 · 입금 2,100 · 연체 229  (8개 테이블)    │
│   "실제로 어떻게 되어 있는가"                          │
├── 레거시 코드 (DB 저장 패키지 pkg_collection) ────────┤
│   청구·연체이자·위약금·충당·연체전환 — 함수 5개          │
│   "실제로 어떻게 계산하는가"                           │
└────────────────────────────────────────────────────┘
```

> "규정·데이터·코드 — 이 셋이 서로 맞는지 아무도 자신 못 하는 상태, 익숙하시죠?
> 오늘 에이전트가 이 셋을 넘나들며 일하는 걸 보여드리겠습니다."

### 0-2. 에이전트 탐색 (선택 — 시간 있으면, 2분)

말로 설명하는 대신 에이전트가 직접 파악하게 시켜도 된다 (→ "사전 지식 없이 레거시를 읽는다"는 인상):

```
이 시스템에 뭐가 있는지 파악해줘 — 테이블 구조랑 저장 함수들, 서로 어떻게 연결돼 있는지.
```

**기대:** 8테이블 + FK 관계 + pkg_collection 함수 5개 요약. 테이블·컬럼·함수에 전부
한글 COMMENT가 달려 있어 에이전트가 의미까지 읽어낸다 (예: `alloc_seq` = "충당 순서…").

> 멘트: "방금 에이전트가 이 시스템을 처음 보고 스스로 파악한 겁니다. 신규 입사자 온보딩이
> 이 속도로 된다는 뜻이기도 합니다." ← 온보딩 지원이라는 프로젝트 목적과 연결

## 장면 2 — 사람 검증 ①: "정말이야?" (SQLTools) ★새 단계

에이전트 말을 그냥 믿지 않고 담당자가 직접 확인:

```sql
SELECT b.contract_id, c.name, c.grade, b.amount
FROM billing b
JOIN loan_contract lc ON lc.contract_id = b.contract_id
JOIN customer c ON c.customer_id = lc.customer_id
WHERE b.bill_type = '중도해지위약금' AND c.grade = 'VIP' AND b.amount > 0;
```

**기대 결과:** 4행 — 계약 63(₩1,460,000) / 133(₩1,060,000) / 203(₩660,000) / 273(₩260,000)

> 멘트: "AI 말을 믿는 게 아니라, **검증하고 씁니다.**"

## 장면 3 — 원인 추적: "왜 생겼어? 또 생겨?" (에이전트) ★하이라이트

```
데이터 정정은 하면 되는데, 왜 생긴 거야? 재발 안 하게 근본 원인을 찾아줘.
위약금이 어느 코드에서 어떻게 계산되는지부터.
```

**기대 응답 (리허설 실측 — 에이전트가 스스로 해냄):**
1. 위약금은 `pkg_collection.f_calc_penalty` 함수가 계산 — 그런데 **고객 등급을 아예 안 봄**
2. 코드 주석 발견: **"등급별 예외(면제)는 영업지원팀 수기 정정으로 운영 중 (2021-06)"**
3. 데이터로 입증: VIP 42건 중 **38건은 수기로 0원 처리, 4건은 빠뜨림**
4. 결론: "수기 정정 관행이 구멍. 근본 원인은 코드에 면제 로직이 없는 것" + 2줄 수정안 제시

> 멘트: "5년 전 '나중에 전산화하자'고 미룬 결정이 수기 정정 구멍으로 돌아왔습니다.
> **사람이 매번 고치는 프로세스는 언젠가 빠뜨립니다.**"

(여유 있으면 언급: 목업은 코드가 DB 안에 있어 직접 읽었지만, 실환경 Oracle 3만 라인은
역문서 엔진이 코드의 대리자 역할 — 이게 역문서화가 필요한 이유)

## 장면 4 — 수정 지시: "그럼 고쳐" (에이전트)

```
회수규정_05에 맞게 legacy_src/pkg_collection.sql의 f_calc_penalty를 수정해줘.
diff를 먼저 보여주고, 내가 승인하면 pg_execute로 배포해.
```

**기대 동작:** 소스 파일 수정 → **딱 2줄짜리 diff** 제시(등급 조회 + VIP면 0원) → **배포 안 하고 승인 대기**

## 장면 5 — 사람 검증 ②: diff 읽고 승인 (사람)

담당자가 diff를 눈으로 읽고(2줄이라 읽을 수 있음) 승인:

```
승인. 배포하고 검증까지 해줘.
```

**기대 동작:** `pg_execute`로 배포 → 에이전트 자체 검증(VIP 42건 전부 0원, 일반 386건은 기존대로 2%)

> 멘트: "**통제는 사람에게 있습니다.** 에이전트는 승인 없이 배포하지 않습니다."

## 장면 6 — 사람 검증 ③: 같은 쿼리, 달라진 결과 (SQLTools)

장면 2에서(또는 시연 시작 때) 돌렸던 쿼리를 **그대로 다시** 실행:

```sql
SELECT pkg_collection.f_calc_penalty(63) AS vip_계약63,
       pkg_collection.f_calc_penalty(7)  AS 일반_계약7;
```

**기대 결과:** 배포 전 `1,460,000 / 340,000` → 배포 후 **`0 / 340,000`**
(VIP만 0으로, 일반은 그대로 — 같은 쿼리의 결과가 눈앞에서 바뀜)
