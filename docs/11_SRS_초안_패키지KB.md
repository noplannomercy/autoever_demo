## 1. 배경과 목적

### 1.1 배경

- 대상 시스템의 비즈니스 로직은 설계 문서가 아니라 **오라클 패키지 바디** 안에 있다. 과거 문서는 유실되어 현재 코드가 유일한 진실이다.
- 코드에 대한 지식이 특정 담당자에게 집중되어 있어, 코드 조회·수정·영향 파악에 사람 의존이 크고 시간이 오래 걸린다.

### 1.2 목적

**패키지 소스를 역문서화하여 검색 가능한 지식베이스(KB)로 만들고, AI 에이전트가 KB·실데이터·소스를 함께 활용해 코드 이해 → 영향 분석 → 디버깅·리팩토링을 지원하게 한다.** 목표 효과는 코드 변경·유지보수 리드타임의 획기적 단축이다.

### 1.3 핵심 설계 원칙 (요구사항 전체를 관통)

| # | 원칙 | 의미 |
|---|------|------|
| P1 | **패키지가 유일한 단위** | 문서화·갱신·적재 모두 패키지 바디 단위. 배포 단위와 일치 |
| P2 | **역문서는 산출물, 코드가 원천** | 문서는 수선하지 않고 다시 뽑는다. 항상 통째 재생성·교체 |
| P3 | **지식의 층 분리** | 코드 사실 = 역문서(KB) · 업무 지식 = 지식층(OKF) · 코드값 = DB 라이브 조회. 서로 섞지 않는다 |
| P4 | **사본 금지** | 살아 있는 원천(DB·git)이 있는 정보는 복사·등록하지 않고 조회한다 |
| P5 | **무정지 파이프라인 + 사후 품질 보증** | 흐름을 막는 승인 게이트 없음. 품질은 자동 검증과 정기 배치 평가가 담당 |
| P6 | **추정 금지** | 코드·DB로 확인 안 되는 내용은 쓰지 않고 "SME 확인 필요"로 태깅 |

## 2. 범위

### 2.1 대상

- **payments / cbreports 도메인의 오라클 패키지 바디 250개** (전체 약 1,690개 중 DB 딕셔너리 의존성 분석으로 추출 완료)
- 제외: 스탠드얼론 프로시저·펑션, 타 도메인 패키지

### 2.2 단계

| 단계 | 기간 | 내용 |
|------|------|------|
| **1단계: 구축** | 준비(현재~8월 중순) + 실행(환경 준비 후~10월) | 250개 역문서화·검증·KB 적재. 절차는 규칙 기반 수동·반자동 |
| **2단계: 운영** | KB 오픈 이후 | Bitbucket 연동 자동 갱신, Pylon 백오피스(배치+대시보드), 사용자 확대 |

### 2.3 제약

- 소스코드 **외부 반출 불가** — 모든 LLM 처리는 고객 환경(AWS Bedrock) 내에서 수행
- LLM 환경(Bedrock)은 **8월 중순 이후** 사용 가능 `[TBD: 계정·리전·모델 확정]`
- 전담 운영 조직 부재 — 1단계는 최소 인력 전제, 2단계 운영 체계는 별도 협의

## 3. 시스템 구성

전 컴포넌트가 기존 자산 또는 표준 기술이며, 신규 발명 요소가 없다.

| 컴포넌트 | 역할 |
|----------|------|
| **Pylon** (최초 진입점) | 역문서화 파이프라인의 배치 잡 실행 + 관리 대장 대시보드(백오피스) — 2단계 |
| **KB** (LightRAG) | 역문서 저장·검색. 문서 적재 한 번으로 벡터·그래프 동시 구축 |
| **지식층** (OKF 표준 문서) | 업무 지식 축적 — SME 답변(smes), 정책·매뉴얼·참고자료(refs). git 버전 관리 |
| **SQLcl (MCP)** | 에이전트의 DB 라이브 조회 — 공통코드, 딕셔너리, 실데이터 |
| **관리 대장** | 패키지 250개의 목록·상태·소스 버전·적재 이력. 1단계는 표, 2단계는 Pylon 대시보드의 원천 |
| **Bitbucket** | 소스 유입 경로. 배포 이벤트가 재문서화 트리거(2단계 자동화) |
| **소비 채널** | 현업·개발자의 질의 창구(에이전트). KB + 지식층 + DB를 합성해 근거와 함께 답변 |

## 4. 요구사항

표기: `R-nn (단계) 제목 — 내용 (출처: US-n)`

### 4.1 문서화 파이프라인

- **R-01 (1단계) 대상 관리** — 문서화 대상은 패키지 바디 단위로 관리 대장에서 관리한다(목록·상태·이력). *(출처: US-1)*
- **R-02 (1단계) 소스 버전 기록** — 역문서 생성 시 원본 소스 식별정보(소스 해시 / LAST_DDL_TIME)를 대장에 기록한다. 모든 이력 추적의 기점. *(출처: US-1, US-13)*
- **R-03 (1단계) 의존성 추출 절차** — DB 딕셔너리(all_dependencies) 기반 대상·참조 추출 쿼리를 재실행 가능한 절차로 유지하고 스냅샷을 보관한다. 재실행·비교가 변경 감지의 입력이 된다. *(출처: US-2, US-9)*
- **R-04 (1단계) 역문서 작성 지침** — ① 코드 사실만 서술(업무 해석 혼입 금지) ② 함수별 섹션 구조로 함수 단위 검색·조회 지원 ③ 판단 불가 항목은 추정 없이 `[SME 확인 필요]` 태깅 ④ OKF 표준 frontmatter. *(출처: US-1, US-14)*
- **R-05 (1단계) 이중 자동 검증** — 생성된 역문서는 ① LLM 저지 채점(소스 대비 누락·과잉·지침 준수)과 ② 실행·데이터 대조(서술된 로직과 실제 동작의 정합)를 거치고, 결과를 대장에 기록한다. *(출처: US-6, US-8)*
- **R-06 (1단계) KB 적재** — 1단계는 검증 통과 문서를 적재한다. 갱신은 항상 문서 단위 교체(기존 삭제 → 신규 적재)이며, 벡터·그래프는 단일 적재로 동시 구축된다. 적재 일시를 대장에 기록한다. *(출처: US-8, US-11)*

### 4.2 갱신·품질 유지

- **R-07 (1→2단계) 갱신 트리거 3종** — ① **코드 변경**: Bitbucket 배포 → 해당 패키지만 재문서화·교체(2단계 자동, 무정지 직행) ② **배치 품질 평가**: 정기 평가에서 미달 판정 문서 재생성 ③ **지침 개선**: 작성 지침 개정 시 구판 일괄 재생성. *(출처: US-3, US-9, US-10)*
- **R-08 (1단계) 재문서화 동일성** — 재생성 문서는 신규 문서와 동일한 지침·검증·적재 절차를 따른다(별도 "패치 문서" 경로 없음). *(출처: US-10)*

### 4.3 지식 관리

- **R-09 (1단계) 지식층 분리** — SME 답변·정책·매뉴얼 등 업무 지식은 역문서에 혼입하지 않고 OKF 문서(smes/refs)로 축적하며, 답변 시점에 KB와 합성한다. 출처(작성자·일시)는 frontmatter에 기록. *(출처: US-4, US-5, US-7)*
- **R-10 (1단계) 코드값 라이브 조회** — 공통코드 등 DB에 존재하는 메타정보는 등록·복사하지 않고 SQLcl로 질의 시점에 직접 조회한다. *(출처: US-4, US-5)*
- **R-11 (1단계) SME 질문 관리** — `[SME 확인 필요]` 태깅 항목을 자동 집계해 질문 목록으로 관리하고, 답변은 지식층에 축적한다. 태깅 잔량의 감소 추이를 KB 성숙도 지표로 보고한다. *(출처: US-6, US-7, US-14)*

### 4.4 운영 (주로 2단계)

- **R-12 (1→2단계) 파이프라인 운영** — 파이프라인은 멱등하게 설계하고(재실행 = 복구), 2단계에 Pylon 배치 잡으로 이관한다. Retry = 잡 재실행, Re-run = 재문서화 잡 실행, Cancel = 잡 중단. *(출처: US-7, US-12)*
- **R-13 (2단계) 대시보드** — 관리 대장을 Pylon 백오피스 화면으로 제공: 패키지별 상태·이력 조회, 저지 점수 하위 문서 선별 확인, SME 태깅 필터, 잡 재실행 액션. *(출처: US-2, US-6, US-12, US-14)*
- **R-14 (1단계) 추적성** — 소스 → 문서 → KB 3단 연결을 대장으로 유지하고, 역문서는 git으로 버전 관리하며, 에이전트 답변에는 근거(출처) 블록을 필수 포함한다. *(출처: US-13, US-15)*
- **R-15 (2단계) 보안·권한·감사** — KB 오픈(사용자 발생) 시점에 SSO·역할 구분을, 백오피스 도입 시점에 액션 감사 로그를 적용한다. 인프라 보안(AWS 계정·Bedrock 접근 통제)은 1단계 환경 구성부터 적용. *(출처: US-15)*

### 4.5 활용(소비) 요구사항 — 이 시스템의 존재 이유

> 유형과 규칙은 데모에서 검증된 동작을 기준으로 확정하고, 목표 수치는 실측 근거가 생기는 시점(드라이런·샘플)에 채운다.

- **R-16 (1단계) 질의 응답** — 에이전트는 KB(역문서) + 지식층(OKF) + DB(SQLcl)를 합성하여 자연어 질의에 답한다. 지원 질의 유형: ① 코드 동작 설명("이 패키지가 뭘 하나") ② 위치 탐색("이 계산이 어느 함수 몇 행에 있나") ③ 영향 분석("이걸 고치면 뭐가 영향받나") ④ 코드·데이터 대조("코드 로직과 실제 데이터가 맞나"). *(데모 검증 패턴)*
- **R-17 (1단계) 답변 신뢰 규칙** — 모든 답변은 근거(출처) 블록을 필수 포함한다(문서명·테이블·식별자). 확인 불가한 내용은 추정하지 않고 "확인 필요"로 답한다 — 원칙 P6의 소비 측 적용. *(출처: US-14, US-15의 취지)*
- **R-18 (1단계) 골든 질의 세트** — 대표 질의 세트를 KB 품질의 상시 측정 기준으로 유지한다. 초기 세트는 드라이런에서 도출하고, 현업 수집 질문으로 확장한다(TBD-6). 목표 정답률 `[TBD: 샘플 실측 후]`.

## 5. 단계별 적용 계획

### 5.1 1단계-준비 (현재 ~ 환경 준비 시점)

환경 없이 가능한 작업. 이 기간의 산출물이 본작업의 속도를 결정한다.

1. 관리 대장 설계·기입 (250개 목록 + 상태·버전 컬럼) — R-01, R-02
2. 추출 쿼리 절차화·스냅샷 보관 — R-03
3. 역문서 작성 지침 확정 (OKF 기반) — R-04
4. 검증 방법 정의 (저지 기준 + 실행 대조 방식) — R-05
5. 드라이런 — 데모 자산으로 파이프라인 전 구간 리허설, 처리 속도 실측 + 골든 질의 초기 세트 도출 (R-18)

### 5.2 1단계-실행 (환경 준비 후 ~ 10월)

1. Bedrock 환경 구성, 샘플 패키지로 절차 재검증 — **이 실측이 TBD-5(목표치)와 §6(완료 기준 수치)의 근거가 된다**
2. 250개 배치 처리 (대장 기반 진행 관리)
3. SME 질문 목록 주기 발송·답변 축적 — R-11
4. KB 적재 완료, 골든 질의 세트로 품질 측정(R-18), 소비 채널 연결 검증

### 5.3 2단계-운영 (KB 오픈 이후)

1. Bitbucket 배포 연동 — 자동 재문서화·재적재 (R-07①)
2. Pylon 배치 잡 이관 + 대시보드 (R-12, R-13)
3. 정기 배치 품질 평가 (R-07②)
4. SSO·권한·감사 로그 (R-15)
5. 사용자 확대 및 지식층 성장 운영

## 7. 가정과 위험

이 계획이 딛고 선 가정들이다. 가정이 깨지면 요구사항 미달이 아니라 **계획 조정 사유**가 된다.

| # | 가정 | 깨졌을 때 | 조기 검증 방법 |
|---|------|-----------|----------------|
| A1 | Bedrock 제공 모델이 PL/SQL 역문서화에 충분한 품질 | 모델 변경 또는 지침 보강, 일정 재산정 | 환경 개통 직후 샘플 5개 실측 (§5.2-1) |
| A2 | SME 질문에 최소 수준의 답변이 이뤄짐 | KB는 코드 사실만으로 가동(중단 없음), 성숙도 지표만 낮게 유지 | TBD-3 채널 협의에서 응답 주기 확약 |
| A3 | 대상 패키지의 배포 빈도가 수동 재문서화로 감당 가능한 수준 | 2단계 자동화(R-07①) 우선순위 상향 | 작업기 중 배포 건수 실측 |
| A4 | 1인 수행 전제 — 파이프라인 자동화 수준이 곧 일정 | 처리량 미달 시 완료 시점 조정 (기준: §6 C1) | 준비기 드라이런에서 처리 속도 실측 |
| A5 | KB 스택의 검색 정확도가 250건 규모에서 유지 | 청킹·적재 방식 조정 (데모는 소규모에서 검증됨) | 적재 누적 구간별 골든 질의 재측정 |
